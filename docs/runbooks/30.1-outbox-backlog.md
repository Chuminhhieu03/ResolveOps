# Runbook 30.1: Outbox Backlog Resolution

> **Severity:** High (Sev-2) / Critical (Sev-1 if backlog age > 1 hour)  
> **Reference:** Master Specification §20.6, §30.1, §24 Phase 16  
> **Owner:** DevOps / Reliability Engineering / Platform Operations

---

## 1. Overview & Detection

ResolveOps utilizes the Transactional Outbox pattern (`outbox_messages` table in SQL Server) to decouple business entity commits from RabbitMQ publication.
When the message broker experiences an outage, high load, or network partition, messages accumulate in `processing_status = 'Pending'` or `'Failed'`.

### Alert Triggers
- **Prometheus / Seq Alert:** `OutboxBacklogAgeSeconds > 300` (Oldest pending message age > 5 minutes).
- **Metric:** `resolveops.messaging.outbox.backlog.size > 1000`.

---

## 2. Diagnostics & Root Cause Analysis

### Step 2.1: Identify Oldest Pending Message and Backlog Depth
Execute in SQL Server management console or `sqlcmd`:

```sql
SELECT
    processing_status,
    COUNT(*) AS total_messages,
    MIN(occurred_at_utc) AS oldest_message_time,
    DATEDIFF(MINUTE, MIN(occurred_at_utc), SYSUTCDATETIME()) AS backlog_age_minutes,
    MAX(processing_attempts) AS max_attempts
FROM outbox_messages WITH (NOLOCK)
WHERE processing_status IN ('Pending', 'Failed')
GROUP BY processing_status;
```

### Step 2.2: Inspect Top Error Categories
```sql
SELECT TOP 10
    event_type,
    last_error,
    COUNT(*) AS failure_count,
    MIN(occurred_at_utc) AS first_failed_at,
    MAX(occurred_at_utc) AS last_failed_at
FROM outbox_messages WITH (NOLOCK)
WHERE processing_status = 'Failed'
GROUP BY event_type, last_error
ORDER BY failure_count DESC;
```

### Step 2.3: Verify RabbitMQ Broker Health
1. Access RabbitMQ Management UI (`http://<rabbitmq-host>:15672`) or run:
   ```bash
   rabbitmqctl status
   rabbitmqctl list_queues name messages consumers
   ```
2. Check if memory alarm or disk free alarm is tripped (`disk_free_alarm: true` or `memory_alarm: true`).
3. Verify worker host connectivity to port 5672.

---

## 3. Mitigation & Recovery Procedure

### Scenario A: RabbitMQ Broker Was Down / Network Partition
1. Once RabbitMQ service is healthy, verify the worker's `OutboxPublisherService` is running.
2. If `OutboxPublisherService` is paused or throttled, trigger an immediate poll or reset backoff:
   ```sql
   -- Reset next attempt for pending messages with backoff delays
   UPDATE outbox_messages
   SET next_attempt_at_utc = SYSUTCDATETIME(),
       processing_status = 'Pending'
   WHERE processing_status IN ('Pending', 'Failed')
     AND processing_attempts < 10;
   ```
3. Observe outbox drain rate in Grafana / Seq. Draining occurs in batches of 100 (`OutboxOptions:BatchSize`).

### Scenario B: Individual Poison Outbox Message Blocking Queue
If a specific message has invalid serialization or schema:
1. Extract the offending payload for offline analysis:
   ```sql
   SELECT id, tenant_id, event_type, payload, last_error
   FROM outbox_messages
   WHERE id = '<message_id>';
   ```
2. Manually isolate the message:
   ```sql
   UPDATE outbox_messages
   SET processing_status = 'DeadLettered'
   WHERE id = '<message_id>';
   ```
3. File a defect ticket with the extracted payload.

---

## 4. Verification & Confirmation

1. Confirm backlog drops to 0:
   ```sql
   SELECT COUNT(*) AS pending_count
   FROM outbox_messages WITH (NOLOCK)
   WHERE processing_status = 'Pending';
   ```
2. Confirm no duplicate side effects in downstream modules:
   - Consumer services enforce transactional `inbox_messages` checking.
   - Verify `inbox_messages` duplicate count metric: `resolveops.messaging.inbox.duplicates`.

---

## 5. Escalation Thresholds

| Backlog Age | Action Required |
|---|---|
| **< 15 min** | Normal automated retry; monitor RabbitMQ queue connection. |
| **15 – 60 min** | On-call engineer paged; verify worker process logs and SQL Server CPU. |
| **> 60 min** | Sev-1 incident; notify Operations Lead; temporarily enable scale-out worker instances. |
