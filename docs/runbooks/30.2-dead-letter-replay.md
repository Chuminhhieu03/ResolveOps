# Runbook 30.2: Dead-Letter Queue (DLQ) Inspection & Safe Replay

> **Severity:** Medium (Sev-3) / High (Sev-2 if DLQ depth > 100)  
> **Reference:** Master Specification §17.3, §20.6, §30.2, §24 Phase 16  
> **Target Queue:** `resolveops.dead-letter` (Bound to `resolveops.dlx`)

---

## 1. Overview & Triggers

When message processing encounters unrecoverable errors (e.g. malformed JSON, schema mismatch) or exceeds the maximum transient retry limit (`RetryLimit = 3`), consumer services execute `BasicNack(requeue: false)`. RabbitMQ automatically routes the rejected message to `resolveops.dlx` with headers indicating the failure context.

### Alert Triggers
- **Seq / Prometheus Alert:** `RabbitMqDlqDepth > 0` on queue `resolveops.dead-letter`.

---

## 2. Inspection & Failure Classification

Connect to RabbitMQ Management UI or use `rabbitmqadmin` CLI:

```bash
rabbitmqadmin get queue=resolveops.dead-letter count=10 requeue=true
```

Inspect the message headers:
- `x-death`: Array containing `count`, `reason`, `queue`, `time`.
- `x-exception-message`: Detailed exception summary.
- `x-original-queue`: Source queue (e.g. `resolveops.notifications`, `resolveops.tracking-events`).

### Classification Matrix

| Failure Category | Symptoms | Action |
|---|---|---|
| **Transient Resource Blip** | DB connection timeout or Redis unavailable during processing. | Safe to replay once dependency is healthy. |
| **Schema / Deserialization** | Missing required JSON properties, invalid enum strings. | Fix producer code or patch payload before replay. |
| **Business Invariant** | Unknown carrier ID, deleted case ID, closed workflow task. | Route to operational investigation; do not blindly replay. |
| **Malicious / Poison** | Huge payload, corrupted bytes, formatting bomb. | Purge from DLQ, record in security incident log. |

---

## 3. Safe Replay Procedure

### Step 3.1: Verify Destination System Health
Ensure the downstream service (API or Worker) and dependencies (SQL Server, Redis, Mailpit/SMTP) are operational.

### Step 3.2: Replay via Dedicated CLI or RabbitMQ Shovel
Using the RabbitMQ Shovel plugin to move messages back to the primary queue:

```bash
# Example: Replay messages from dead-letter to resolveops.notifications
rabbitmqadmin declare parameter component=shovel name=requeue-notifications \
  value='{"src-queue": "resolveops.dead-letter", "dest-queue": "resolveops.notifications", "prefetch-count": 10, "requeue": false}'

# Verify shovel processed messages
rabbitmqadmin list parameters component=shovel

# Delete shovel parameter once queue is drained
rabbitmqadmin delete parameter component=shovel name=requeue-notifications
```

### Step 3.3: Idempotent Verification
Because consumers implement transactional `inbox_messages` checking using `messageId = $"{CorrelationId}_{EventType}_{ConsumerName}"`, messages that already executed partial side effects will NOT duplicate database writes or emails.
