# Runbook 30.6: Cross-Tenant Data Leak Suspicion & Incident Response

> **Severity:** Critical (Sev-1)  
> **Reference:** Master Specification §0 Rule 14, §10.6, §19.4, §30.6, §24 Phase 16  
> **Owner:** Security Incident Response Team (SIRT) / Lead Architect

---

## 1. Overview & Immediate Response Policy

Cross-tenant isolation is the highest architectural invariant of ResolveOps.
Any report, automated alert, or suspicion that User from Tenant A was able to view, query, mutate, export, or download data belonging to Tenant B triggers an immediate **Severity-1 Emergency Response**.

---

## 2. Immediate Containment Procedure (Phase 1: 0–15 Minutes)

### Step 2.1: Isolate the Affected Feature / Endpoint
If a specific endpoint or feature is suspected (e.g. an export endpoint or dynamic reporting query):
1. **Disable via Feature Flag** (if managed by FeatureManagement) or block via reverse proxy (Nginx / API Gateway):
   ```nginx
   # Example: block specific endpoint temporarily in Nginx
   location /api/reports/carrier-scorecards {
       return 503 "Service temporarily unavailable for emergency maintenance.";
   }
   ```
2. If the vulnerability is pervasive across the API:
   - Temporarily scale down API instances or switch to maintenance mode while investigating.

### Step 2.2: Preserve Forensic Traces & Logs
**DO NOT purge, restart without memory dumps, or overwrite log files.**
1. Export all Seq logs for the incident time window (`T - 2 hours` to `T + 1 hour`).
2. Snapshot the current SQL Server audit tables and `outbox_messages` / `inbox_messages`.
3. Snapshot Redis cache keys matching the affected tenants:
   ```bash
   redis-cli --scan --pattern "tenant:<tenant_a_id>:*"
   redis-cli --scan --pattern "tenant:<tenant_b_id>:*"
   ```

---

## 3. Investigation & Scope Assessment (Phase 2: 15–60 Minutes)

### Step 3.1: Analyze JWT Claims and Authentication Context
Verify if the issue was caused by:
- Stale or spoofed `tenant_id` claim in JWT.
- Missing `tenant_id` check in an EF Core query bypassing global query filters (`.IgnoreQueryFilters()` used improperly).
- Missing `@TenantId` parameter in a Dapper raw query.
- Misconfigured MinIO presigned URL generator allowing arbitrary S3 keys.

### Step 3.2: Determine Affected Data Scope
Run forensic queries in SQL Server to find any records accessed by non-owner tenant users:
```sql
SELECT
    al.id,
    al.tenant_id AS request_tenant_id,
    al.user_id,
    al.action_type,
    al.entity_name,
    al.entity_id,
    al.created_at_utc,
    al.details
FROM audit_logs al WITH (NOLOCK)
WHERE al.created_at_utc >= @IncidentStartTime
ORDER BY al.created_at_utc DESC;
```

---

## 4. Remediation & Code Patching (Phase 3)

1. Identify root cause in code.
2. Add an explicit failing test case in `tests/ResolveOps.PerformanceTests/Security/TenantIsolationSecurityTests.cs`.
3. Fix the query filter, authorization handler, or cache key prefixing.
4. Verify the test passes.
5. Invalidate all Redis caches for the affected tenants:
   ```bash
   redis-cli EVAL "return redis.call('del', unpack(redis.call('keys', ARGV[1])))" 0 "tenant:<tenant_id>:*"
   ```
6. Force global logout of all active sessions for the affected tenant by revoking their `RefreshTokenSessions`:
   ```sql
   UPDATE refresh_token_sessions
   SET is_revoked = 1,
       revoked_at_utc = SYSUTCDATETIME()
   WHERE tenant_id IN ('<tenant_a_id>', '<tenant_b_id>');
   ```

---

## 5. Notification & Post-Mortem (Phase 4)

1. Executive / Legal notification: Notify Legal Counsel and compliance officers within regulatory windows (e.g. GDPR 72-hour notice, HIPAA, SOC 2).
2. Customer notification: Deliver formal incident report to affected tenant administrators detailing:
   - Nature of the incident
   - Exact records accessed (if any)
   - Containment and permanent remediation actions taken
3. Document post-mortem in `docs/security/incidents/INC-<YYYYMMDD>-TENANT-LEAK.md`.
